# MT7925U port plan

The MT7925 is MediaTek's Wi-Fi 7 USB part (Netgear Nighthawk A9000, A8500, and MediaTek
reference sticks). It receives 160 MHz, which the MT7921 cannot, and every 6 GHz access
point measured in the reference house runs 160 MHz ([docs/TESTING.md](TESTING.md)). That is
the reason to port. This page records what the upstream driver says the port involves, checked
line by line against `openwrt/mt76` at the pinned baseline `c5a3bd91`, so that the work is a
transcription like the MT7921 driver was, not a reverse-engineering project.

Nothing here has been run on MT7925 hardware. Every statement is either a citation into the
mt76 source or an explicit hypothesis to test on the first day the adapter is attached.

## What the source says

Claims below came from a third-party summary of the port; each was checked against the source.

| Claim | Verdict | Evidence at `c5a3bd91` |
|---|---|---|
| A9000 is USB `0846:9072` | Verified | `mt7925/usb.c:20-22`; also `0e8d:7925`, `0e8d:6639`, A8500 `0846:9050` |
| Wi-Fi on interface 0, Bluetooth on interface 1 | Not determinable | mt76 never reads `bInterfaceNumber`; it binds by class `ff/ff/ff` and assigns endpoints positionally (`usb.c:303-328`), requiring exactly 2 bulk IN and 6 bulk OUT |
| Firmware `WIFI_MT7925_PATCH_MCU_1_1_hdr.bin`, `WIFI_RAM_CODE_MT7925_1_1.bin` | Verified, path differs | `mt792x.h:49,57`, under `mediatek/mt7925/`; present in linux-firmware at the pinned commit. Chip ID `0x6639` needs the MT7927 RAM blob instead (`mt7925/usb.c:219-224`) |
| Same multi-stage firmware handshake | Verified | `mt792x_core.c:980-1036` is shared; connac3 takes the same patch/RAM/semaphore path (`mt76_connac_mcu.c:3245`) |
| Same USB framing and MCU mailbox | Partly | Same TXD structs, but a forked filler (`mt7925/mcu.c:3645-3734`) that omits `MT_TXD1_LONG_FORMAT` and changes UNI ack options; the reply header is 44 bytes, not 36 (`mt7925/mcu.h:26-42`), so every parsed response offset shifts by 8 |
| Register offsets move for DMA and MAC control | Contradicted for the USB path | `mt792xu_dma_init`, EP4 routing, `MT_UDMA_*`, `MT_SWDEF_MODE`, `MT_CONN_ON_MISC` are shared (`mt792x_usb.c`, `mt792x_regs.h:397-508`); `mt7925/regs.h` redefines none of them. The one fork is the WFSYS reset triple (`mt792x_usb.c:375-391`) |
| `mt7925_mcu_set_chan` configures 160 MHz | Contradicted as stated | There is no channel-switch driver op on MT7925; monitor tuning is SNIFFER enable + config only (`mt7925/main.c:1967-1969`), and that TLV is byte-identical to MT7921's (`mt7925/mcu.c:2298-2327`) |
| RX descriptor overhauled for EHT | Verified, larger than claimed | connac3 (`mt76_connac3_mac.h`): 32-byte base, GROUP bits 16-20, FCS error moves to RXD3, group sizes 16/16/16/16/96, RCPI at P-RXV word 3 (`mt7925/mac.c:460-551`) |
| Need 64 KB transfers and 16 to 32 queued URBs | Contradicted | Upstream queues 128 URBs of at most 4 pages, MCU queue one page, RX aggregation left off on both chips (`mt76.h:674`, `usb.c:357-407,709-716`, `mt792x_usb.c:399-410`) |
| 320 MHz on the A9000 | Not for this chip | `is_320mhz_supported` is `0x7927` only (`mt76_connac.h:261-264`); 160 MHz is unconditional on 5 GHz (`mt7925/init.c:290-292`) |

## What transcribes directly

- USB device selection by class and endpoint shape, not interface number. This is roadmap R2
  and it precedes the port; the interface 0 versus 3 question is answered by the descriptor.
- `mt792xu_dma_init`, DMASHDL prefetch, EP4 event routing, firmware-download gating on
  `MT_UDMA_TX_QSEL`.
- Patch and RAM download, patch semaphore, scatter on the `AC_BE` endpoint, `N9_RDY` poll.
- Both SNIFFER messages, including the width table (20/40 to 0, 80 to 1, 160 to 2) and the
  SCA/SCB rule.
- URB sizing and aggregation-off.

## What must change

1. **Firmware paths** under `mediatek/mt7925/`, chosen after reading `MT_HW_CHIPID`.
2. **WFSYS reset**: reset register `0x70028600`, done register `0x184c1604` compared whole-word
   against `0x00001d1e`, 20 ms settle, no status-select write (`mt792x_regs.h:420-426`).
3. **MCU framing**: no `MT_TXD1_LONG_FORMAT`; QUERY_ACK versus EXT_ACK by command; 44-byte reply
   header, so the patch-semaphore status byte is at offset 40 and the UNI status event at 44.
4. **Command encoding**: efuse buffer mode, RX filter, and NIC capability move from EXT/CE to UNI
   with tag+length prefixes (`MCU_UNI_CMD(EFUSE_CTRL)` tag 2, `BAND_CONFIG` tag `0x0C`,
   `CHIP_CONFIG` tag 3). Delete the `MCU_EXT_CMD(CHANNEL_SWITCH)` call; the SNIFFER CONFIG TLV
   is the channel command.
5. **Start sequence**: MT7925 issues neither `SET_MAC_ENABLE` nor `SET_RX_PATH`
   (`mt7925/main.c:339-362`); do not carry them over.
6. **RX decode**: a connac3 variant of `rxd.decode`, not a patch. Fields and sizes above.
7. **NIC capability** parsing changes to an element list (`mt7925/mcu.c:1085-1116`).

## Hypotheses to test on day one

- **Composite layout.** Record the full descriptor set with pyusb before claiming anything.
  Pick the interface with class `ff/ff/ff` and exactly 2 bulk IN plus 6 bulk OUT endpoints.
- **macOS Bluetooth contention.** The summary claims `bluetoothd` can latch the device. On the
  MT7921 the Wi-Fi interface is claimed without touching the Bluetooth interfaces and it works;
  test whether the same holds on the A9000 by claiming only the Wi-Fi interface and checking
  `ioreg` for what owns the Bluetooth one. No kernel or DriverKit extension is planned.
- **160 MHz capture throughput.** Measure with `scripts/retune_drops.py` and a busy 160 MHz AP
  before changing the synchronous read loop; the current driver reads one 8 KiB transfer at a
  time and that ceiling has not been measured on any chip.
- **Chip ID.** Read `MT_HW_CHIPID` first; an A9000 that reports `0x6639` needs different blobs.

## Sequencing

R2 descriptor discovery first, then a `Mt7925uDevice` beside `Mt7921uDevice` sharing the USB
and firmware-download layers, then a `rxd_connac3` decoder with synthetic fixtures built from
the connac3 header, then hardware smoke on 20/80/160 MHz with the existing redacted schema.
The recorded-USB corpus (R20) should be captured from both chips so the two paths stay in
agreement.

## Reading order

1. `mt7925/usb.c`: probe, MCU send, reset.
2. `mt792x_usb.c` and `mt792x_regs.h`: shared USB bring-up and the MT7925 reset triple.
3. `usb.c`: `mt76u_set_endpoints`, RX queue allocation.
4. `mt792x.h` and `mt792x_core.c`: firmware names and `mt792x_load_firmware`.
5. `mt7925/mcu.c` and `mt7925/mcu.h`: `mt7925_mcu_parse_response`, `mt7925_mcu_fill_message`,
   the UNI tag enums, sniffer and efuse commands.
6. `mt76_connac3_mac.h` and `mt7925/mac.c`: the descriptor and `mt7925_mac_fill_rx`.
7. `mt7925/init.c` and `mt7925/main.c:339-362`: init and start sequence.
